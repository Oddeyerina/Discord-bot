# Architecture

The dashboard calls FastAPI with JSON and a signed HTTP-only session cookie. FastAPI owns configuration writes. The bot reads configuration from the shared SQLite database in WAL mode and writes only runtime records such as ticket state, XP, panel message IDs, and task results. The bot sends guild channel, role, and emoji snapshots to the API's internal sync endpoint using `SESSION_SECRET`. This endpoint is outside `/api` and requires the internal header.

Each panel feature stores its embed and target channel in `panels`. Ticket and reaction-role panels have multiple named rows per guild. Their config routes list, create, update, and delete panels by ID; deletion marks a panel inactive and queues deletion of its Discord message. Publishing queues `post_panel` or `update_panel` in `bot_tasks`. The bot claims pending tasks about every two seconds and records `done` or `failed`. A saved `message_id` makes later publishes edit the existing panel message. Guild data sync runs at startup and every five minutes.

## Ticket flow

Each ticket panel's Open Ticket button sends an ephemeral picker for that panel's reasons. If priorities are configured, the user then chooses one in a second ephemeral picker. The bot creates a private thread in the same panel channel, prefixes its name with the reason emoji when set, and adds the opener and members holding the reason's support roles. It posts the info embed with persistent Claim, Close, Change priority, Quick Reply, Assign to me, Unassign, Add note, and View notes buttons. The info embed shows the selected priority with its emoji when set. If the reason has questions, the bot posts one numbered questions embed with a persistent Done button attached to that message. Only the opener can click Done. The bot disables it and pings the configured support roles once. If the reason has no questions, the bot skips that message and pings support immediately. `answered_at` and `pinged_at` record the notification step in either case. Support staff can claim or assign the ticket, change its priority, send a quick reply, and record notes. Assignment supersedes the claim in the info embed. Notes are stored in `ticket_notes` and posted as `[NOTE]` messages without a ping; they are visible to everyone in the private thread and included in the transcript. The first nonempty message by the opener is checked against configured auto-response keywords; the bot sends matching responses only for that first message. An hourly sweep warns the opener after the configured inactivity warning period and closes the ticket after the inactivity limit, unless disabled. Closing archives and locks the thread, saves a plaintext transcript, posts it to the configured transcript channel with opened and closed timestamps, duration, assignee, and priority, and marks the ticket closed.
Claimed tickets use a distinct `ticket:claim:claimed` custom ID for their disabled Claim button. Both claimed and unclaimed views are registered at bot startup, so the disabled state remains correct after restarts.

Discord adds users, rather than roles, as private-thread members. The bot expands the configured support roles to their members when opening the ticket. The same role IDs are used for the notification after Done or immediately when no questions exist. Existing SQLite databases receive the `answered_at`, `pinged_at`, and `priority_id` ticket columns and the priority `emoji` column during API startup. Phase B migration also removes panel uniqueness and adds panel names, ticket panel scopes, multiple welcome auto roles, Remembering label embeds, and the Temp Voice control channel. Priorities remain as inactive rows when removed from configuration so existing tickets retain their references. `ticket_first_replies` records which opener message triggered auto-response matching.
If support roles change while tickets are open, the API keeps the original reason row for those tickets and creates a new row for future tickets, so the Done ping reaches the members added when each ticket opened.

## Added features

- Sticky Messages store channel, optional ping role, embed, and cooldown in `sticky_channels`. After the cooldown, the bot deletes the previous sticky and posts a new one so it appears at the bottom of the channel. This delete-and-repost behavior is intentional; stickies are neither pinned nor edited. **Sticky now** queues a `post_sticky` task, and **Resend all stickies** refreshes every enabled sticky. The current message ID and last post time are runtime fields. Failed posting tasks expose an error to the dashboard while saved configuration remains stored.
- Temp Voice stores hub settings in `tempvoice_config` and created channels with their owners in `tempvoice_active`. Joining the hub creates a private voice channel and moves the member; an empty temporary channel is removed. Members use the guild-scoped `/tempvoice` commands in the configured control text channel while connected to their temporary voice channel. Renaming preserves a leading emoji. The owner can rename it, change its user limit, lock or unlock public access, and delete it. A connected member can claim ownership only after the current owner leaves; the bot transfers the channel permission overwrite and updates `owner_id`.
- Sticky Roles records a departing member's assignable roles in `sticky_roles_saved` and restores valid roles on rejoin, excluding configured roles. The saved row remains for future joins.
- Remembering Dates are entered by members with `/birthday set`, `/birthday remove`, and `/birthday list`. A daily 08:00 UTC check uses the configured IANA timezone and `remembered_announcements` to avoid duplicate posts for the same local day. Announcement embeds support `{user}`, `{label}`, and `{age}` when a year is stored. A label-specific embed overrides the default when configured. February 29 is announced only in leap years.

## Member slash commands

The guild command tree exposes `/rank [user]` (member to check; defaults to yourself), `/stats [user]` (level, XP, messages, join date, and roles), `/leaderboard xp` (top 10 by XP), and `/leaderboard messages` (top 10 by messages). `/birthday set <day> <month> [label] [year]` saves a recurring date: day is 1–31, month is selected from January through December, label defaults to Birthday, and optional year is 1900–2100. `/birthday remove [label]` removes a saved date by label (default Birthday); `/birthday list` shows saved dates. Invalid calendar dates and future years are rejected. All responses are ephemeral.

The Levels cog grants voice XP once per minute to human members sharing a non-AFK voice channel with another human. Ignored voice channels and the per-minute amount come from `level_config`. Tracking begins when the bot sees a voice join or starts up; disconnected time is never backfilled. `level_users.messages_count` increments when a message earns XP.

Moderation commands `/warn <user> <reason>`, `/warns <user>`, `/clearwarns <user>`, `/mute <user> <duration> <reason>`, `/unmute <user>`, `/ban <user> <reason> [delete_messages_days]`, `/kick <user> <reason>`, `/slowmode <seconds>`, `/lock [channel]`, and `/unlock [channel]` use Discord permission checks and ephemeral replies. Warning thresholds, optional DM, the log channel, and `log_mod_actions` (default true) are configured on `/dashboard/moderation`. The moderation cog listens for native Discord ban, unban, member removal, and timeout update events. It checks up to five audit log entries for a matching target within ten seconds; a member removal is treated as a kick only when the audit log confirms it. Slash commands mark their own actions for thirty seconds so their event listeners do not post duplicate embeds. When audit log access fails, the bot logs a warning and posts the event embed without moderator details; kick detection cannot then separate a kick from an ordinary departure. This feature requires View Audit Log permission. Rules verification uses a persistent `verify:agree` button; `/post-rules` and the dashboard queue or post the configured embed in the rules channel. The button grants the configured role and replies privately.

The bot records `bot_last_seen` in `app_meta` every 30 seconds. `/api/health/detail` reports API, database, and bot status for the overview card. On startup, running tasks are requeued and missing Temp Voice channels and panel channels are cleaned up. A daily `db_maintenance` task removes old completed and failed tasks and vacuums SQLite. The backup script uses SQLite's online backup command. Successful dashboard writes are recorded in `audit_log` and shown on `/dashboard/audit`.

Temporary voice owners use `/tempvoice name <name>` (new channel name, 1–100 characters), `/tempvoice limit <limit>` (user limit, 0–99; zero means unlimited), `/tempvoice lock` (deny connect for everyone), `/tempvoice unlock` (allow connect for everyone), and `/tempvoice delete` (delete the channel). A connected member can use `/tempvoice claim` after the owner leaves. These responses are ephemeral.

`/help` reads the guild command tree and groups member commands by feature. `/help`, `/userinfo [user]`, and `/serverinfo` return public embeds. `/poll <question> <option1> <option2> [option3…option10] [duration] [multi]` posts a native Discord poll publicly in the current channel. Question length is 1–300 characters and each answer is 1–55 characters. Discord's native poll API uses whole-hour durations; choices start at one hour.

`/event create <title> <date> <time> [description] [type] [channel] [duration_minutes]` parses Europe/Berlin local time into UTC. **Message only** posts an announcement embed, **Discord event only** creates an external scheduled event, and **Both** does both with a link in the embed. `scheduled_events` stores both Discord IDs, the creator, and the UTC start; FastAPI creates the table on startup. `/event list` reads upcoming rows and `/event cancel <id>` checks creator or administrator status before deleting the Discord event, marking an announcement cancelled when possible, and removing the row. Public announcements are posted in the selected channel; command confirmations are ephemeral. The bot needs Create Events and Manage Events permissions for Discord scheduled events.

The command tree's global error handler logs unhandled slash-command exceptions and sends ephemeral feedback, including cooldown and permission errors. It uses a follow-up if the command has already acknowledged the interaction.

The Stats cog reads `stats_config`, counts members, voice activity, boosts, and configured roles, and edits an existing stats embed on its configured interval. Missing messages are recreated. `{online}` counts online humans and requires Presence Intent; `{in_voice}` also excludes bots. Stats placeholders include `{total_members}`, `{human_members}`, `{bot_members}`, `{online}`, `{in_voice}`, `{artist_count}`, `{verified_count}`, `{booster_count}`, `{boost_count}`, `{boost_level}`, `{boosts_needed}`, `{timestamp}`, and `{role_count_<label_slug>}`. Embed title, description, and footer also resolve matching `#channelname` and `@rolename` references after normal placeholder substitution. `resend_all_stickies` forces a refresh of all enabled sticky messages.

The API owns feature configuration through authenticated routes. The bot writes runtime rows and timestamps through the shared SQLite file. Voice channels and categories are included in guild data sync for dashboard dropdowns.

Tables include `guild_id` so the schema can support more than one server later. The current API and UI use the configured `DISCORD_GUILD_ID` only. Credentials are a single environment-configured admin account; multi-user auth is outside Phase 1.

## Adding a feature

1. Add configuration and runtime tables in `api/models.py`, plus Pydantic input schemas in `api/schemas.py`.
2. Add a focused router in `api/routers/` and register it in `api/main.py`. Apply session authentication through the common router registration.
3. Add a cog in `bot/cogs/` and load it from `bot/main.py`. Read settings from SQLite. Use `bot_tasks` when a dashboard action must be executed in Discord.
4. Add a dashboard page under `web/app/dashboard/` and a navigation entry in `web/lib/navigation.ts`. Reuse `useConfig`, dropdowns, and `EmbedEditor`.
5. Document permissions, settings, and behavior. Introduce migrations before changing tables in an existing deployment; SQLAlchemy's initial schema creation does not alter existing tables.
